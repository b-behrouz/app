# اصلاح GitHub Pages — آمادهٔ بررسی، هنوز منتشر نشده

نشانی هدف: https://b-behrouz.github.io/app/

## علت واقعی

آخرین انتشارِ موجود با workflow داخلی `pages build and deployment` از کامیت `e2894e6ab771e33de37777204b71e198062aad4a` ساخته شده است:
https://github.com/b-behrouz/app/actions/runs/40330904121

لاگ build ورودی‌های `ref: main`، `source: .` و `destination: ./_site` را ثبت کرده است. در مخزنِ آن نسخه فایل `index.html` در ریشه وجود نداشت؛ خروجی برنامه فقط `hamghadam-preview.html` نام داشت. Jekyll افزونهٔ `jekyll-readme-index` و مولد `JekyllReadmeIndex::Generator` را اجرا کرد و README را به index تبدیل کرد.

artifact همان انتشار (`github-pages`، شناسهٔ `12654867249`) دانلود و بررسی شد: عنوان `هم‌قدم — نسخهٔ مستقل محلی | app` دارد و فاقد `div#root` برنامه است. بنابراین علت، نبودن ورودی سایت در ریشه و فعال‌بودن fallback مستندات Jekyll است؛ عنوان README یا کش مرورگر علت اصلی نیست.

خواندن تنظیمات Pages از API در ابزار اتصال فعلی پشتیبانی نمی‌شود؛ منبع بالا از ورودی‌های اجرای واقعیِ آخرین انتشار تأیید شده است. خواندن لینک زنده در این محیط نیز با محدودیت شبکه روبه‌روست. ادعای بررسی تازهٔ رابط زنده نداریم.

## اصلاح آماده‌شده

- `index.html` در ریشهٔ همین منبع، بایت‌به‌بایت برابر آخرین `hamghadam-preview.html` است.
- `.nojekyll` پردازش Jekyll و تبدیل README به صفحهٔ اصلی را غیرفعال می‌کند. README و بقیهٔ مستندات حذف نمی‌شوند.
- مسیریابی داخلی موجود HashRouter حفظ شده است: `/app/#/feedback` و `/app/#/centers/ibn-sina-mashhad` نمونه‌های معتبرند؛ رفرش این URLها همان index ریشه را دریافت می‌کند.
- برای ورود مستقیم URLهای معمولی، پوشهٔ ورودی هر صفحه و هر ۱۷ پروفایل موجود ساخته شده است؛ مثلاً `/app/feedback/` و `/app/centers/ibn-sina-mashhad/` با پاسخ واقعی فایل index همان پوشه به مسیر hash متناظر منتقل می‌شوند. این مسیرهای شناخته‌شده به fallback با وضعیت HTTP 404 وابسته نیستند.
- `404.html` فقط مسیرهای قدیمی/ناشناختهٔ دیگر را زیر پیشوند `/app/` به روتر می‌سپارد. در GitHub Pages پاسخ اولیهٔ مسیر ناشناخته همچنان HTTP 404 است؛ مسیرهای شناخته‌شده فایل مستقل دارند.
- پیشوند در `config/pages.json` ثبت شده است. تمام منابع نمایشی داخل HTML هستند و به `/assets` ریشهٔ دامنه یا فایل جانبی متکی نیستند.
- هیچ تغییری در JavaScript، استایل‌ها، محتوای رابط یا متادیتای HTML اصلی انجام نشده است. ورودی اصلی از ابتدا client-rendered بود؛ این اصلاح، پیش‌رندر موجودی را حذف نکرده است. فایل‌های ورود مستقیم، رابط جدید یا بازطراحی نیستند و فقط URL را به روتر فعلی می‌سپارند.

## ساخت و پیشگیری از بازگشت مشکل

```sh
python3 scripts/build_preview.py
python3 scripts/build_pages.py
python3 scripts/check_project.py
python3 -m unittest discover -s tests -p test_pages_build.py
```

یا `npm run build` هر دو خروجی را می‌سازد. برای بازکردن HTML محلی هیچ‌یک از این دستورها لازم نیست.

`build_pages.py` فهرست خروجی‌ها را در `.pages-manifest.json` ثبت می‌کند. چک عادی و چک staged، سازگاری index و تمام ورودی‌ها با سورس را کنترل می‌کنند. workflow بررسی نیز خروجی Pages و ورود مستقیم و رفرش زیر `/app/` را در مرورگر می‌آزماید. اسکریپت پایان درخواست فقط بعد از تأیید کاربر و با `--approved-push` اجرا می‌شود و ساخت Pages و فایل‌های تولیدی را هم در همان کامیت قرار می‌دهد.

workflow انتشار فعلیِ شاخه‌ای حفظ می‌شود؛ workflow انتشار موازی ساخته نشده تا دو منبع با هم رقابت نکنند. انتشار از `main` و `/(root)` بعد از push تأییدشده انجام خواهد شد. تنظیمات حساب در این مرحله تغییر نکرده است.

## بعد از تأیید صریح صاحب پروژه

1. تغییرات همین درخواست و قواعد تأییدِ محلیِ قبلی بررسی، commit و بدون force push ارسال شوند.
2. اگر تنظیمات هنوز مطابق آخرین اجرای موجود باشد، تغییری توسط صاحب حساب لازم نیست: **Repository → Settings → Pages → Build and deployment → Deploy from a branch → main → /(root)**. صرفاً در صورت اختلاف تنظیمات، ابتدا علت اختلاف بررسی شود؛ تغییر به GitHub Actions برای راه‌حل فعلی لازم نیست.
3. اجرای Pages تا پایان دنبال و artifact آن از نظر وجود index برنامه بررسی شود.
4. خود نشانی زنده، عنوان و رابط برنامه، جست‌وجو، ناوبری، پروفایل/گالری و رفرش لینک‌های مستقیم بررسی شوند. سبزشدن workflow به‌تنهایی رفع مشکل زنده محسوب نمی‌شود. اگر سیاست شبکه مانع بررسی لینک زنده شد، محدودیت گزارش شود و موفقیت زنده ادعا نشود.

هیچ push، اجرای انتشار یا تغییر تنظیمات Pages پیش از تأیید صریح انجام نشده است.

## نتیجهٔ بررسی این مرحله

- آزمون مرورگر روی خروجی استاتیکِ آماده‌شده زیر `/app/` در اندازه‌های موبایل و دسکتاپ موفق شد: صفحهٔ اصلی، جست‌وجو، اعمال و پاک‌کردن فیلتر، پروفایل و گالری، فرم‌ها، پشتیبانی، ورود مستقیم و رفرش مسیرهای شناخته‌شده؛ هیچ مسیر شناخته‌شده‌ای پاسخ 404 نگرفت.
- ۶ آزمون Python (ساخت Pages و کنترل اسرار)، کنترل سازگاری خروجی و آزمون منطق ثبت شیت موفق شدند.
- آزمون تازهٔ `file://` در مرورگر این محیط با `ERR_BLOCKED_BY_ADMINISTRATOR` مسدود است. خود فایل پیش‌نمایش بدون تغییر بایت نسبت به فایل قبلاً تأییدشدهٔ CI باقی مانده است؛ گالری و فیلتر در آزمون تازهٔ خروجی استاتیک نیز کنترل شدند، اما این آزمون به‌عنوان اجرای تازهٔ `file://` معرفی نمی‌شود.
- فایل HTML خصوصی قبلاً بارگذاری‌شده در Drive، پس از ساخت مجدد بایت‌به‌بایت با آخرین پیش‌نمایش تطبیق داده شد؛ چون اصلاح فقط بسته‌بندی و انتشار را تغییر می‌دهد، محتوای بصری HTML همان نسخهٔ اصلی است.
- خواندن مستقیم سایت زنده و API تنظیمات Pages در محیط فعلی محدود است. تا پیش از تأیید و انتشار، رفع مشکل زنده اعلام نمی‌شود.
